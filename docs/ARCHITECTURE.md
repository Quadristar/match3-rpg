# ARCHITECTURE.md(alcyon-game-template)

ブラウザ 2D ゲーム用の雛形の設計ドキュメント。
設計を変更した場合は、このファイルと `CHANGELOG.md` を更新すること。

このファイルは、雛形から作成した各ゲームのリポジトリにもそのまま引き継がれ、
「共通基盤の設計書」として使われる。ゲーム固有の設計は、各ゲームの `docs/GAME_DESIGN.md` に書く。

---

## 1. 目標

- PC・スマートフォンのブラウザで動く 2D ゲームの共通基盤
- 高品質な静止画(立ち絵・背景)を、演出(フェード・拡大縮小・揺れ・発光・パーティクル・カメラ演出など)で魅力的に見せるゲームを前提とする
- 総容量が大きくなっても、必要な素材だけを段階的に読み込む
- Claude Code が何度変更・拡張しても壊れにくい構造

---

## 2. 技術構成

| 技術 | 状態 | 用途・方針 |
|---|---|---|
| TypeScript | Phase 1 で導入 | `strict`。AIの変更ミスを型エラーとして検出する |
| Vite | Phase 1 で導入 | 開発サーバー・ビルド。本番ではビルド成果物のみを配置する。`base` は相対パス(`./`) |
| PixiJS | Phase 1 で導入 | 描画。レンダラは **WebGL に固定**(WebGPU は端末差が大きいため当面使わない) |
| Vitest | Phase 1 で導入 | ユニットテスト。スマホのみの開発環境で品質を保つ中心 |
| ESLint | Phase 1 で導入 | コード品質と、**モジュール間の依存境界の強制** |
| GSAP | 基盤拡張時に導入候補 | 演出タイムライン。`presentation/` でのみ使用 |
| Howler.js | 基盤拡張時に導入候補 | 音声。モバイルの音声アンロック、音量グループ、フェード |
| pixi-filters | 必要時に導入 | 発光・ブラー・色調変化 |
| Spine | 導入しない | 表示部品を差し替え可能にしておき、将来の導入に備える |

## 3. レイヤー構造

```
┌─────────────────────────────────────────────┐
│ presentation  描画・演出・UI・シーン          │  Pixi などに依存
├─────────────────────────────────────────────┤
│ app           起動、シーン管理、各層の接続     │  すべてを知る唯一の層
├─────────────────────────────────────────────┤
│ services      アセット・音声・セーブ・入力・    │  外部ライブラリをラップ
│               設定・レイアウト                  │
├─────────────────────────────────────────────┤
│ systems       ゲームロジック(純粋TS)          │  各ゲームで実装・テスト対象
│ data          型付きゲームデータ              │  各ゲームで実装
│ core          汎用基盤                        │
└─────────────────────────────────────────────┘
```

依存ルール(ESLint の `no-restricted-imports` で強制):

- `core`: 外部依存なし
- `data`: `core` のみ
- `systems`: `core`, `data` のみ(描画・音声・時刻・`Math.random` に依存しない)
- `services`: `core` と外部ライブラリ
- `presentation`: `core`, `systems`(主に型), `services`, 外部ライブラリ
- `app`: すべて

## 5. 主要モジュールの責務

- **Game**: Pixi Application の生成、サービスの初期化、SceneManager の起動。ゲームルールは知らない
- **SceneManager**: シーンを `enter / exit / update / resize` のライフサイクルで管理する。シーン切り替え時のトランジションと、`exit` 時のアセット・表示オブジェクトの解放を共通化する(シーン任せにしない)
  - シーンが従う型(`Scene` / `SceneContext` / `SceneFactory`)は `presentation/scenes/Scene.ts` に置く(`presentation` は `app` を import できないため)
  - シーンはキーで登録し、使うときに生成する。フェードは Pixi の ticker で進める(GSAP は使わない)
  - 切り替え中の別の要求: フェードアウト中は行き先を上書き、enter 待ち・フェードイン中は最新の1つを保留(仮仕様)
- **EventBus**: 型付きの通知に使う。ロジックの主経路には使わない(処理の流れが追えなくなるため)
- **StateMachine**: シーン内の進行管理などに使う汎用の状態機械
- **SeededRng**: シード付き乱数。ゲームロジックの乱数はすべてこれを使う
- **ObjectPool**: 頻繁に生成・破棄する表示物(パーティクル・数字表示など)の再利用

## 6. 画面の向きとレイアウト

- 縦画面・横画面の両方に対応する
- 論理解像度は向きごとに持つ(仮仕様: 縦 720×1280、横 1280×720)
- 実際の画面にはアスペクト比を保って拡大縮小し、余白は背景で埋める
- **LayoutManager** が向きを判定し、向きごとの**レイアウト定義**を提供する
  - 領域: 画面をどう区切るか(ゲームごとに定義を差し替える)
  - 基準点: 演出の位置指定に使う名前付きの座標
  - セーフエリア(画面の切り欠き)を考慮した領域
- 向きの切り替え時は、登録されたビューに再配置を通知する
- 描画の構成(背面から): 背景レイヤー(画面座標・余白を含む画面全体)→ ゲーム用ルート(論理座標・拡大縮小される)→ フェード用の覆い
- 画面サイズとセーフエリアから配置を求める計算は、DOM・Pixi に依存しない純粋な関数(`services/layout/computeLayout.ts`)に分け、テストする
- URL に `?debug&safearea=上,右,下,左`(CSS ピクセル)を付けると、セーフエリアを上書きできる(動作確認用・仮仕様。§9 参照)
- 回転時は、再生中の演出を即座に完了させてから配置し直す
- 背景イラストは、縦長・横長どちらでトリミングしても成立するよう、広めに描いて重要な要素を中央に寄せる

## 7. アセット管理

- マニフェストにバンドル単位(`boot` / `common` / シーン別 / ステージ別 …)で登録する
- 起動時に読み込むのは `boot` のみ
- AssetManager は Pixi の `Assets` をラップし、次を担当する
  - バンドル単位のロードと進捗通知
  - 参照カウントによる重複読み込み防止と解放
  - ロード失敗時の再試行とフォールバック
- 構成(`services/assets/`)
  - `AssetManager`: 参照カウント・重複防止・再試行・フォールバック・失敗の記録。読み込み処理(`AssetLoader`)を外から受け取るため、Pixi なしでテストできる
  - `pixiTextureLoader`: Pixi の `Assets.load` / `Assets.unload` で画像を読み込み・破棄する
  - 同じファイルを複数のバンドルが含む場合は、どのバンドルも使わなくなるまで解放しない
- 失敗時: 設定回数だけ再試行し(仮仕様: 2回、500ms 間隔)、最終的に失敗したら
  - `boot` … 起動エラーを表示する
  - それ以外 … 代わりの画像(マゼンタと黒の市松模様)で続行する
  - どちらも失敗を記録する(コンソールとデバッグ表示)
- シーンとの連携: シーンは `bundles` で必要なバンドルを宣言する。SceneManager が enter の前に読み込み、exit の後に解放する
  - 旧シーンのバンドルは、新シーンのバンドルを読み込んだ後に解放する(共通のバンドルを読み直さないため)
  - 読み込みが長引いたら(仮仕様: 300ms)、読み込み中表示(文字と進捗バー)を出す
  - 読み込み中の切り替え要求は保留し、表示後に切り替える(読み込みは中断しない。仮仕様)
- アセットのキーは型付き定数とし、コードにファイルパスを直接書かない
- 形式(仮): 画像は WebP、BGM は m4a または ogg、効果音は短い mp3

## 8. メモリ管理

- GPU メモリはファイル容量ではなく **縦×横×4バイト** で消費される(2048×2048 で約16MB)
- 目安(仮仕様): 立ち絵は長辺 2048px 以下、背景は論理解像度の1.5倍以下、テクスチャは1辺 4096px 以下
- 描画解像度は `devicePixelRatio` をそのまま使わず上限2とし、低品質設定では1.5にする
- 頻繁に生成する表示物は ObjectPool で再利用する
- シーン終了時の破棄処理を SceneManager で共通化する

## 9. パフォーマンス

- 目標は安定した 60FPS
- URL に `?debug` を付けると、FPS・推定テクスチャメモリ・表示オブジェクト数・画面の向きと論理解像度・読み込み済みのバンドルと参照数を表示する(スマホでの唯一の計測手段)
  - `presentation/debug/`。`?debug` がないときは生成も更新もしない。表示の更新は 250ms ごと
  - 推定テクスチャメモリは AssetManager が読み込んだ画像の 縦×横×4 の合計。テキストや図形から生成されるテクスチャ、描画先の画面のバッファ、代わりの画像は含まない
  - `?debug` と併用できるパラメータ(仮仕様。`?debug` がないときは無視する)
    - `safearea=上,右,下,左` … セーフエリアの上書き
    - `assetfail=バンドル名,…` … 指定したバンドルの読み込みをわざと失敗させる
    - `assetdelay=ミリ秒` … アセット1つごとに読み込みを遅らせる(上限 10 秒)
    - `quality=low|medium|high` … 起動後に品質プリセットを切り替える(設定として保存される)
    - `savefail` … 保存の書き込みをわざと失敗させる
  - 品質プリセットと描画解像度、保存の状態(正常/メモリ上で動作中)も表示する
- 品質プリセット(低・中・高)で、パーティクル上限・フィルタ・描画解像度を切り替えられるようにする
- 本格的な最適化は計測でボトルネックを確認してから行う

## 10. 入力

- Pointer Events でマウスとタッチを統一する
- InputManager はタップ・ドラッグ・スワイプ(方向付き)を検出する
- 入力はゲームごとに「操作の意図」へ変換してからロジックに渡す(キーボード対応を後から追加しやすくするため)
- 構成(`services/input/`)
  - `GestureRecognizer`: 判定の純粋なロジック(DOM 非依存・テスト対象)。しきい値は画面座標で判定する(指の実際の移動量のため)
  - `InputManager`: 判定結果を論理座標に変換して通知する。一時停止は停止要求の数を数え、すべて取り下げられたら再開する
  - `attachPointerInput`: DOM の Pointer Events をつなぐ。スクロール・ズーム・長押しメニューを抑止する
- 同時に扱う指は1本だけ。`pointercancel` と一時停止の開始時は、操作中の指を取り消す(`cancel` を通知)
- スワイプは `dragend` の後に続けて通知し、開始位置と方向を渡す
- シーンは `context.input` で入力を受け取る。登録と一時停止はシーンの exit で自動的に解除される。シーン切り替え中は SceneManager が一時停止する
- しきい値(仮仕様): ドラッグ開始 10px、タップ 300ms 以内、スワイプ 50px 以上かつ 500ms 以内(`gameConfig.ts`)
- キーボードを追加するときは、入力元を足し、`InputEvent` に種類を足す
- UI(Button・Panel)への入力(`presentation/ui/`)
  - Pixi のイベントシステムは使わない(初期化時に無効化し、DOM のイベントも外す)。入力は InputManager に一本化する
  - InputManager は、ジェスチャーの判定より先に「ポインタ処理」に指を渡す。ポインタ処理が指を独占した場合、その操作はゲーム側(`context.input.on`)に渡らない
  - シーンごとに `UIInputRouter` がポインタ処理として自動で登録され(exit で解除)、シーンの root の中の最も手前の UI 対象を探す
  - 手前の判定は描画順(子は親の後、兄弟は後ろの子ほど手前)。zIndex による並べ替えは考慮しない(仮仕様)
  - 当たり判定は画面座標を各対象の `toLocal` で変換して行う(親の拡大縮小・移動に追従する。回転も含む)
  - ボタン: 指を置いたら押下中の見た目、ボタンの上で離したら実行。外に出たら見た目を戻し、離しても実行しない
  - 非表示(自分か親の visible / renderable が false)のボタンは反応しない。無効なボタンは反応しないが、背後にも入力を通さない(仮仕様)
  - Panel は上に置いたものの背後への入力を遮る。モーダルな Panel の表示中は、Panel の外も含めて背後のボタンやゲーム側に入力を渡さない

## 11. 音声

- AudioManager が BGM・効果音・ボイス・UI音を管理する
- 音量はカテゴリ別(BGM・効果音・ボイス)とマスター、ミュートを持つ
- シーン変更時の BGM 切り替えとフェードを担当する
- モバイルの自動再生制限は、最初のタップ(「タップしてスタート」画面)で解除する

## 12. セーブ

- セーブデータには最初から**バージョン番号**を持たせ、形式変更時は移行処理を書く
- 保存先は当面 localStorage。容量が必要になれば IndexedDB に移行できるよう SaveManager で抽象化する
- 設定(音量・品質)の保存も SaveManager を通す
- 雛形が扱うのは保存・読み込み・移行の仕組みまで。保存する中身は各ゲームが定義する(`SaveSchema`)
- 保存キーは「ゲーム ID:キー」。GitHub Pages では同じドメインの全ゲームが localStorage(と約5MB の容量)を共有するため、ゲーム ID で区別する。ゲーム ID は `gameConfig.ts` の1か所で変える
- 保存形式は `{"version": 数値, "data": 中身}`。読み込み時に `migrations[n]`(n → n+1)を順に適用し、移行したら書き戻す
- 異常時(仮仕様。どれもゲームを止めない)
  - 読めないデータ(壊れている・新しすぎる・移行できない・形が違う) … 元の文字列を「キー.corrupt」に退避してから初期状態で始める。退避に失敗したら元のデータは上書きしない
  - 保存先を使えない・書き込めない … メモリ上のデータで動作を続け、状態を「メモリ上で動作中」にする。問題は記録し、デバッグ表示に出す
- 設定(`services/settings/`): 音量(マスター・BGM・効果音・ボイス)・ミュート・品質プリセット
  - 音量は 500ms 変化がなくなってから保存し、ミュートと品質はすぐ保存する。ページを閉じる・裏に回るときにも保存する
  - 品質プリセットは描画解像度の上限(高・中: 2、低: 1.5)につながり、実行中に切り替えて反映する
  - 初期値(仮仕様): 音量 マスター 1.0・BGM 0.8・効果音 0.8・ボイス 1.0、ミュートなし、品質「中」

## 14. 新しいゲームを始める手順

詳しい手順は `docs/NEW_GAME.md` にある(雛形から作ったリポジトリでやり直す GitHub の設定、デモを最小の形に置き換えるコード例を含む)。要点:

1. このリポジトリで「Use this template」を押し、ゲーム用のリポジトリを作成する
2. ゲーム側の Settings → Pages で Source を「GitHub Actions」にする
3. `src/app/gameConfig.ts` の `gameId` と `package.json` の `name` をゲーム固有の値に変える
4. `presentation/scenes/demo/` と `public/assets/demo/` を削除し、`src/presentation/game/` と最初のシーンに置き換える
5. ゲーム用の `CLAUDE.md` に差し替え、`docs/GAME_DESIGN.md` を追加する。README に雛形のバージョンを記録する
6. `docs/ARCHITECTURE.md` はこの雛形のものをそのまま使う
7. `main` のブランチ保護ルール(Rulesets)を作る

雛形を更新したときは `CHANGELOG.md` を確認し、必要な変更を各ゲームへ手動で取り込む。
